## DEPLOY-001：取得真正可恢复的材料

### 根因

旧 `persist_backup` 验证的是内存 `Manifest::parse` 和默认流字节哈希，而恢复 `open_regular` 还检查实际属性、硬链接、ADS、可信 ACL 等。NTFS 目录的 compression state 会被新文件/子目录继承；`FILE_ATTRIBUTE_NORMAL` 并不清除这种继承。因此写侧可以接受自己恢复读侧必拒绝的材料，随后继续安装。字节存在不等于能由程序恢复。

### Auto 决策

选择**拒绝不支持压缩备份环境**，不单独放宽备份压缩白名单，也不改共用 `open_regular` 的属性限制：

1. `Context` 验证实际备份根属性；`persist_backup` 重新验证根及新子目录，不支持的可继承属性（含压缩、加密）在改目标前报错。不自动解压、不更改既有目录 ACL/压缩设置。
2. `persist_backup` 最后调用与 `restore()` 共用的 `load_backup`，读取**实际落盘的整份** manifest/两槽载荷，检查目录与文件属性、可信 owner/DACL、普通单硬链接、无 ADS、存在性、长度/哈希、schema/SD 结构和目标目录身份/模式。
3. 再比较读回 manifest 的序列化结果与本次拟保存内容，防止读回合法但非预期状态。
4. 用 `VerifiedBackup` 保留已绑定备份目录及 manifest/载荷读句柄，禁止其他写入/删除共享，直至该备份或事务操作结束。`backup()` 也不能返回未经此门禁的材料；恢复前新建的恢复点同样走此路径。
5. 根目录预检失败不新建唯一备份；已建子目录后失败则留现场并明确“目标尚未修改”。不扫描、覆盖或删除未知文件。目标/staging/source 的旧属性拒绝策略不变。

代价：新增一次完整恢复读取/哈希和若干持有句柄/有界缓冲；这是“先有可恢复材料”的证明性成本，不以省 I/O 为由移除。仍不能保证恶意管理员、设备不兑现 Flush、掉电或磁盘满下的跨文件原子性。

## DEPLOY-002：名字可以变，对象不能换

### 根因

旧 `PinnedDirectory` 只有 metadata 访问；省略 `FILE_SHARE_DELETE` 不构成目录名锁。采集 A 的 ID/mutex 后，`Files`、输入、备份、暂存及 rename 目的地仍重新解析全路径字符串，可转而访问旧名处的 B。核心保存代码的对象绑定并不覆盖部署内部链路。

### 对象绑定设计

| 活动链路 | 本轮实现 |
| --- | --- |
| 目录建立/定位 | 只对本地盘符根锚点用 `CreateFileW`；之后每级都是 `NtCreateFile(RootDirectory=前一级已验证句柄)` |
| 目录验证 | 实际磁盘目录、非 reparse；单组件 UTF-16 名，拒绝分隔符、ADS、`.`/`..`、设备名、尾点/空格；原路径上限仍 240 |
| 防 reparse | Native 对象属性 `OBJ_DONT_REPARSE`，创建选项 `FILE_OPEN_REPARSE_POINT`，不接受按字符串重试 |
| 身份/mutex/目标快照 | `Context` 从绑定目标对象采 ID、建 mutex；`Files` 的两次打开均相对同一目标句柄 |
| 输入 | `source_parent` 逐级绑定后，相对打开唯一输入叶子；后续只从返回文件句柄读取 |
| 备份创建/验证 | 根对象内 `FILE_CREATE` 创建唯一子目录；载荷、manifest、共用恢复读侧都相对这个子目录句柄，不重新从其文本路径定位 |
| 选定旧备份 | 恢复只在绑定 `c.root` 内按已校验备份叶子相对打开，然后全程持有同一选定目录及读取句柄 |
| 暂存 | 正向/回滚副本都相对绑定目标对象唯一创建，metadata 重开也相对该对象并核对卷/文件 ID；保留原 protected DACL 精确创建策略 |
| 存在性/目录项核对 | 相对已绑定父目录打开单叶子核对 ID；不再以 `GetFileAttributesW` 或最终路径文本代表目录项归属 |
| 提交/补偿 | `NtSetInformationFile(FileRenameInformation=10)`，公开 WDK 布局的 `RootDirectory=目标句柄`、单叶子、`ReplaceIfExists=false`；原实体 unlink 与清理仍只走已持有文件句柄 |

所有 Native 文件句柄使用 `SYNCHRONIZE` + `FILE_SYNCHRONOUS_IO_NONALERT`，保留原同步 I/O、BackupIntent、分享访问、私有线程按需特权重试与 RAII。Native 失败显式映射 `RtlNtStatusToDosError`，异常同时保留原 NTSTATUS；不依赖 Native API 不保证设置的 `GetLastError`。

SDK `winternl.h` 提供 `NtCreateFile`/基础类型，但未提供所用 rename 声明/结构；按官方 `NtSetInformationFile` 签名和 `FILE_RENAME_INFORMATION` 布局作局部声明，x64 字段偏移有静态断言。只从进程已加载的系统 `ntdll.dll` 取导出，不搜索其他 DLL、不新增下载/第三方库、不改根 CMake；接口不可用即失败，无不安全路径回退。当前 Win32 `FILE_RENAME_INFO` 文档也允许相对 RootDirectory，本实现选择显式 Native 结构以保持该链路一致，并非声称 Win32 文档必定禁止它。

目录共享允许改名，以明确不依靠“锁名字”。原路径核查保留为创建后、备份返回、首次 unlink 前和事务清理前的安全拒绝/诊断检查，**不是 TOCTOU 正确性的唯一依据**。核查后若再发生变更，Native 相对 I/O 仍只涉及已验证对象，不能访问旧名处 B；回滚继续使用同一父对象，不先按旧字符串找另一目录。文件属性/ACL 的持续可信还依赖系统可信目录 ACL，恶意管理员不属于隔离目标。

名字变化可能使返回/诊断路径不再可用；实现通常在检查点拒绝并按已知对象回滚，不承诺给并发维护后的新路径自动重新授权、重新绑定或跨机器恢复。原双文件可捕获异常补偿、混合态拒绝、备份留存及非掉电原子性边界不变。

## 确定性观察点的限制与用法

观察回调仅显式线程本地注册，先要求目标已注册为合法虚拟 SACL 沙箱、当前用户拥有，再存目标目录 ID；运行点还必须模式为 false 且绑定 ID 匹配。回调重入被抑制；system 模式在调用任何回调前返回。没有环境开关、清单/GUI 开关或权限绕过。调用者负责回调/context 寿命，并在结束/异常后 `set_observer({}, nullptr, nullptr)`。

注册目录白名单保留旧 `LexHelper-deploy-tests-<32 hex>`，仅另允许本轮专用 `D:\temp\aiRunner\opencode\LexHelper-fix-backup-<14 位数字>-<32 hex>` 内当前用户拥有的目录，便于把新开发材料限于一个可清理边界。真实 SACL 不被模拟写入；目标字节、ACL、硬链接、压缩/reparse/rename 都是实际 NTFS API。

最小交错形态（在自有目录内）如下；这不是修改旧测试的许可：

```cpp
deploy_testing::enable_security_simulation(target);

    [](auto point, const std::filesystem::path& subject, void* context) {
```

4. [NtSetInformationFile](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/ntifs/nf-ntifs-ntsetinformationfile)、[FILE_RENAME_INFORMATION](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/ntifs/ns-ntifs-_file_rename_information)：用户态用 Nt 名称，FileRenameInformation=10、DELETE、RootDirectory+简单相对名、不覆盖及结构布局。
5. [FILE_RENAME_INFO](https://learn.microsoft.com/en-us/windows/win32/api/winbase/ns-winbase-file_rename_info)：当前 Win32 文档也允许相对 RootDirectory；没有引用已失效的“必须 NULL”断言作为设计依据。
