## 范围与方案选择

- 实际修改：`src/core/io.cpp` 的 `import_file` 和紧邻局部类型判定 helper；`docs/核心格式与边界.md` 增加入口契约；README 增加一条格式识别说明；本报告。
- `save_impl`、Native 目录对象、安全输出和公开 API 不变；核心 parser、测试、header、CMake、`.localdoc` 均未修改。不继续委派，不 commit/push。
- 问题：合法无 BOM 词前码后文本的首词 `PK`、`WBC1/2/3`、`imscwubi` 被 ASCII 前缀当成二进制类型。英文词条合法，不能通过强制 BOM、注释或中文限制规避。

比较方案：

| 方案 | 决定与原因 |
|---|---|
| 仅将 `PK` 改成完整 ZIP magic | 不足；仍误判 WBC/lex 英文词条 |
| 二进制 parse 报错后 catch 再尝试文本 | 拒绝；隐藏损坏或非新世纪输入的原错误 |
| 所有未知扩展都拒绝/强制用户改名 | 拒绝；无必要缩窄原有未知/无扩展文本能力 |
| 只看扩展名，不保留内容识别 | 拒绝；丢失原有 `.bin` 等二进制按内容导入能力 |
| **显式类型优先 + 完整 ZIP 标记 + 可打印魔数的文本包络消歧** | **选用**；保持类型明确、严格解析一次和未知类型兼容 |

最终次序（扩展名仅 ASCII 大小写不敏感，不依赖用户 locale）：

1. `.txt/.tsv` 直达 `read_text`，BOM 可选；`.cwb/.lex/.wbc3` 固定分别走 `read_cwb/read_lex/read_wbc3`，类型冲突直接拒绝。显式二进制扩展不能由 BOM 或其他 magic 偷换类型。
2. 其余（包括 `.bin/.wbc`、未知/无扩展）先按 UTF-8/UTF-16 BOM 选文本；UTF-16BE 仍拒绝。再按完整 `PK 03 04`、`PK 05 06`、`PK 07 08` 选 ZIP/CWB；不因此新增空 CWB 或分卷支持。
3. 对未知类型的 `imscwubi/WBC1/WBC2/WBC3`：全文件含 TAB，且不存在小于 0x20 的字节（TAB/CR/LF 除外），才有文本包络；交给 `read_text` 做完整严格校验。其他魔数输入按相应二进制解析，WBC1/2 明确拒绝。完整受支持 lex/WBC 头含 NUL，不可能满足该文本包络；截断后未形成合法表仍整体失败。
4. 其余仍交给 `read_text`。该包络不验证 Unicode、不截断输入、不跳坏行、不吞错误；坏 UTF-8/代理项/NUL/坏行/重复项仍由既有 parser 拒绝。只有实际解析成功才生成对应的 `source`。

兼容性说明：普通未知/无扩展文本能力未缩窄，魔数词条文本获得修复；真实未知扩展 lex/WBC/CWB 仍按内容识别。以前 magic 可能覆盖 `.cwb`，或把其他二进制内容装进 `.lex/.wbc3/.txt` 后仍成功的行为，现在作为显式类型冲突拒绝，这是有意明确类型，而非支持任意改名文件。未知类型的内容若已经完全成为合法规范文本，无法还原其历史是否曾为二进制；固定二进制扩展用于表达强制类型。没有增加 Rime YAML 或其他新格式。
